A short walkthrough of RAG — and of a project that answers questions about a PDF it has never been trained on.

PDF→ Chunks→ Vectors→ Search→ Answer

01 · Intro

Prompts got easier. Context got harder.

Two years ago, squeezing a good answer out of a model was a craft: magic words, rigid formats, clever tricks.

Models improved. Today a plain, honest question usually works. Prompt engineering did not disappear — it just stopped being the bottleneck.

The real limit moved. A model can only reason about what it can see, and it cannot see:

  • Your company's documents
  • Anything after its training cutoff
  • Private, internal, or brand-new data

Ask a perfect question about a document the model never read, and you get a perfect-sounding invention. The missing piece is context, not phrasing.

01 · Intro

So: how do we hand the model the right context?

We could paste the whole document into every prompt. That is slow, expensive, and eventually too big to fit.

The better idea: find only the few passages that matter for this question, and send just those.

That idea has a name — RAG.

02 · What is RAG

Retrieval-Augmented Generation

Before answering, retrieve relevant material from an external source, augment the prompt with it, then let the model generate.

Question→ Retrieve→ Augment→ Generate→ Grounded answer

The model stays the same. We only change what it is looking at when it answers — an open-book exam instead of a memory test.

02 · What is RAG

Why it is worth the effort

🎯

Fewer hallucinations

Answers are grounded in real passages — and you can show which ones.

🔄

Always current

Update the documents, not the model. No retraining, no fine-tuning.

🔐

Private data, safely

Your files stay in your database; only the needed snippet travels.

💸

Cheap

3 small chunks in the prompt instead of 300 pages.

🔍

Traceable

Every answer points back to a page and a chunk.

🧩

Model-agnostic

Swap the LLM tomorrow; the knowledge base stays.

02 · What is RAG

And MCP? Same family.

MCP (Model Context Protocol) is a standard way to plug models into external tools and data sources.

RAG

Fetches context from a knowledge base you prepared — documents turned into vectors.

MCP

Fetches context from live systems — a database, an API, a file system, a ticket tracker.

Different plumbing, same principle: the model does not know — it is told, at answer time. MCP is, in spirit, RAG with a protocol and live sources.

03 · The Project

Chat with a PDF, in the terminal

A Node + TypeScript CLI that ingests a PDF once, then answers questions about it — grounded, cited, and entirely from that document.

📃 Read & chunk→ 🧠 Embed→ 🛢 Store→ 🔍 Search→ 🤖 Answer

First three steps run once, at seeding time. The last two run on every question.

03 · The Project — Step 1

Read the PDF, break it into chunks

1

LangChain's PDFLoader extracts the text page by page. Then RecursiveCharacterTextSplitter cuts it into pieces of 1000 characters with 200 of overlap.

Why chunk at all? A whole book is too big to send and too vague to match. A chunk is small enough to be about one thing — which is exactly what makes it findable.

Why overlap? So a sentence split across the boundary is not lost — it survives in the neighbouring chunk.

Each chunk keeps its metadata: page number, position, source file. That is what makes answers citable.

03 · The Project — Step 2

Turn each chunk into a vector

2

An embedding model reads a chunk and returns a list of numbers — a vector that represents its meaning.

Similar meanings land close together in that space, even with completely different words. "rabbit" sits near "hare"; "tea party" sits near "Hatter".

Here the model is Xenova/all-MiniLM-L6-v2, running locally through Transformers.js — no API call, no cost, no data leaving the machine.

This is the core trick: comparing numbers is how a computer compares meaning.

03 · The Project — Step 3

Store the vectors in a vector database

3

Every chunk is saved in Neo4j (Docker) as a Chunk node holding its text, its metadata, and its vector — indexed for similarity search.

Why not a normal database?

SQL answers "where does this value match exactly?". It has no idea that "hare" is close to "rabbit".

What a vector DB adds

It answers "what is closest in meaning?" — and does it in milliseconds over millions of vectors, using an index instead of comparing one by one.

A vector database is the memory of a RAG system. Without it, semantic search does not scale past a toy.

03 · The Project — Step 4

The question becomes a vector too

4

When the user asks something, the question goes through the same embedding model. Then the database returns the 3 nearest chunks (topK: 3) with a similarity score.

Chunks scoring below threshold: 0.7 are dropped. If nothing survives, the app says so instead of guessing — "I don't know" is a valid answer.

"Who is the Hatter?"→ [0.12, -0.44, …]→ top 3 chunks

03 · The Project — Step 5

Join the chunks, send them as context

5

The 3 chunks are concatenated into a single context block and injected into a prompt template alongside the user's question, the assistant's role, tone, and rules.

One rule matters most: answer only from the provided context. That is the line between a grounded answer and a confident invention.

The LLM is reached through OpenRouter, so the model behind the answer is just an environment variable.

03 · The Project — Stack

Two libraries doing the heavy lifting

🤗

Hugging Face

The public catalogue of open models. We pick an embedding model from it and run it locally via Transformers.js.

all-MiniLM-L6-v2 — small, fast, free, and good enough for semantic search. Swapping it is a one-line change in .env.

🦜

LangChain

The glue. It gives us the PDF loader, the text splitter, the Neo4j vector store, the prompt template, and the chain that wires retrieval into generation.

RunnableSequence = retrieve → generate, as two composable steps.

Recap

The whole idea in one line

Don't teach the model your data — hand it the right page at the right moment.

  • Prompts stopped being the bottleneck; context took over
  • RAG = retrieve → augment → generate
  • Chunks + embeddings + a vector database make meaning searchable
  • 3 relevant paragraphs beat 300 irrelevant pages
